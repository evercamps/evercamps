# Writing an EverCamps plugin

A plugin is a self-contained, independently-buildable extension that lives outside `core/`
and `includes/`, in its own folder under `content/plugins/<name>`. It's the same idea as a
WordPress plugin dropped into `wp-content/plugins`: you never edit core files, you register
your folder and the framework's bootstrap lifecycle, routing, GraphQL schema stitching and
webpack build all pick it up automatically.

Two real plugins already live here and are worth reading alongside this doc:

- **`national-number-field`** — minimal example. A single field injected into an existing
  admin page area, a server-side validation hook, a GraphQL type extension and one migration.
  No API routes, no new pages.
- **`woocommerce-import`** — fuller example. API routes, its own settings page, GraphQL
  types + resolvers, services, and multiple migrations.

## How a plugin gets loaded

Every plugin must be **registered** in `config/default.json` under `system.extensions`:

```json
{
  "system": {
    "extensions": [
      {
        "name": "my-plugin",
        "resolve": "content/plugins/my-plugin",
        "enabled": true,
        "priority": 100
      }
    ]
  }
}
```

- `name` must be unique across plugins and core modules (`includes/bin/lib/loadModules.js`) —
  the loader throws on a collision.
- `resolve` is the path to your plugin folder, relative to the repo root.
- `priority` controls load order — lower runs first.
- `enabled` is the default state; see "Enabling / disabling" below for how this interacts
  with the admin UI.

In **development**, the loader (`includes/bin/extension/index.ts`) requires a `src/` folder
under `resolve` and compiles it with `swc` on the fly (via the dev watcher). In **production**,
or when `resolve` contains `node_modules` (an npm-installed plugin), it requires a prebuilt
`dist/` folder instead. In practice this means: always ship both a `compile` script and commit
to running it before a production build.

## Enabling / disabling a plugin

There are two layers:

1. **`config/default.json`** is where a plugin is *registered* and its default `enabled` value
   lives.
2. **The admin UI** at `/plugin-management` lets an admin toggle a registered plugin on/off
   without editing JSON. This writes a DB override into the `setting` table
   (`plugin_enabled.<name>` = `'1'`/`'0'`) that takes precedence over the config default —
   see `includes/bin/extension/pluginOverrides.ts` and `getPluginEnabledOverrides()`.

Toggling from the admin UI does **not** live-reload the running process — the extension list
is resolved once at boot (`initExtensions()`, called at the very start of `dev`/`build`/`start`)
and memoized for the lifetime of the process. The UI shows a "restart required" badge when the
DB-effective state differs from what's actually running; the change takes effect on the next
restart. Core modules (the hardcoded list in `loadModules.js`) are never toggleable — only
plugins registered under `system.extensions` show up as toggleable in that UI, and the toggle
endpoint (`core/modules/setting/api/updatePluginStatus`) rejects any name that isn't one.

Disabling a plugin never deletes its data and never un-applies its migrations — migrations are
forward-only, and re-enabling a plugin does not re-run migrations that already applied.

## Anatomy of a plugin folder

```
content/plugins/my-plugin/
├── package.json         # name, "type": "module", compile + typecheck scripts
├── tsconfig.json          # rootDir "src", outDir "dist"
├── src/
│   ├── bootstrap.ts         # entry point, run once at boot — see below
│   ├── lib/                  # framework-free helper code
│   ├── services/               # business logic
│   ├── pages/
│   │   └── admin/<routeName>/    # one folder per page/area override, see "Pages"
│   ├── api/
│   │   └── <routeName>/           # one folder per REST-ish endpoint, see "API routes"
│   ├── graphql/
│   │   └── types/<TypeName>/       # one folder per GraphQL type, see "GraphQL"
│   └── migration/
│       └── Version-1.0.0.ts          # DB schema changes, see "Migrations"
└── dist/                 # compiled output (generated by `npm run compile` in this folder)
```

`content/plugins/*` is also an npm workspace (declared in the root `package.json`), so a
plugin can have its own `dependencies` and gets them installed by the root `npm install`.

`package.json` for a new plugin, matching the two existing ones:

```json
{
  "name": "evercamps-my-plugin",
  "version": "1.0.0",
  "main": "index.js",
  "type": "module",
  "description": "...",
  "scripts": {
    "compile": "swc src -d dist --config-file ../../../.swcrc --copy-files --strip-leading-paths",
    "typecheck": "tsc --noEmit"
  }
}
```

`tsconfig.json` — copy `content/plugins/national-number-field/tsconfig.json` as a starting
point; the important bits are `"rootDir": "./src"`, `"outDir": "./dist"`, `"jsx": "react"`.

## The bootstrap file

`src/bootstrap.ts` is your plugin's entry point. The framework imports it once at boot and
calls its default export — an async function taking no arguments and returning `void`. This is
the *only* place you're allowed to register hooks, value processors and widgets; doing so from
anywhere else (e.g. a middleware) throws, because the registries lock themselves after boot.

```ts
export default async (): Promise<void> => {
  // register processors / hooks / widgets here
};
```

If your plugin doesn't need to hook into anything at boot (e.g. it only adds pages/API routes
that are self-sufficient), an empty async function is fine — see `woocommerce-import`'s
`bootstrap.ts`.

### Value processors — the main extension point

Most core write-paths run their input through a named, pluggable value pipeline
(`includes/lib/util/registry.ts`). Add a processor to intercept and transform (or validate) a
value before it's used:

```ts
import { addProcessor } from '.../dist/lib/util/registry.js'; // see "Reaching framework code" below

addProcessor('participantDataBeforeCreate', (data) => {
  // mutate/validate and return data
  return data;
}, 20); // priority — lower runs first, must be < 1000
```

`addFinalProcessor` reserves the last slot (priority 1000) and throws if one is already taken —
use it when your plugin must be the last word on a value. Look at where a value name is defined
in the module you want to affect (grep for `getValue(` / `getValueSync(`) to find the exact hook
point and its shape.

### Function hooks — wrapping a named function

For wrapping an entire function call (not just a value), use `hookBefore`/`hookAfter`
(`includes/lib/util/hookable.ts`) against the function's name, as registered via `hookable()`
in core.

### Widgets

`registerWidget` / `updateWidget` / `removeWidget` (`includes/lib/widget/widgetManager.ts`)
register CMS-configurable widgets (a `type`, a `component` and `settingComponent`, both
resolvable `.js` paths whose filename starts with an uppercase letter). `updateWidget` lets a
plugin override a core widget's component.

## Pages — new admin/front-store pages or overriding an existing page area

Every page or page-area component lives in `src/pages/admin/<routeName>/` (or
`src/pages/frontStore/...`). Two conventions:

- **A brand-new page** needs a `route.json` (`{ "methods": ["GET"], "path": "/my-page" }`),
  an `index.ts` that sets page metadata via `setContextValue(request, 'pageInfo', {...})`, and
  one or more `.tsx` components exporting `layout = { areaId, sortOrder }` to place themselves
  into that page's layout areas (commonly `areaId: 'content'`).
- **Overriding/extending an existing page** (no new route) — drop a component into the same
  folder name/area an existing page already renders, e.g.
  `pages/admin/participantEdit+participantNew/MyField.tsx` with
  `layout = { areaId: 'participantEditGeneral', sortOrder: 25 }`. No core files are touched;
  the area-scanning mechanism picks it up purely by folder location + the `layout` export.

A component can fetch its own data by exporting a `query` (a GraphQL query string) alongside
the component — see `Plugin.admin.graphql`'s consumer `Grid.tsx` for the pattern:
`url(routeId: "...")` resolves a registered route's URL, and any of your GraphQL fields can be
queried directly.

React/webpack-bundled files (anything under `pages/` or `components/`) resolve framework and
shared UI code through webpack aliases, **not** relative `dist` paths:
- `@components/...` — any component file under a `components` folder in core, the active theme,
  or an enabled extension, keyed by its path after `components/` (e.g.
  `@components/form/Field`, `@components/admin/cms/Card`).
- `@evercamps/evercamps/lib/...` → `includes/lib/...`
- `@evercamps/evercamps/components/...` → `includes/components/...`

## API routes

`src/api/<routeName>/route.json`:

```json
{ "methods": ["POST"], "path": "/my-plugin/do-thing", "access": "private" }
```

The path is automatically prefixed with `/api`. `access` is `"private"` (admin session
required) or `"public"`. The sibling handler file (any name, default export
`(request, response, next) => {...}`) does the work; if you call `next` without invoking it
(3-arg arity), the framework's auto-`next()` call is skipped so you can send your own response
without a double-`response.json()` crash — see `woocommerce-import`'s `importProducts.ts` for
the exact pattern, and its `[context]bodyParser[auth].ts` sibling for wiring a JSON body
parser. There is no GraphQL mutation convention in this codebase — all writes go through
REST-ish routes like this one, called from the admin UI via `axios`.

## GraphQL

`src/graphql/types/<TypeName>/<TypeName>.graphql` + a `.resolvers.ts` sibling extend the
schema — `extend type Query { ... }` / new `type Foo { ... }`. Use the `.admin.graphql` /
`.admin.resolvers.ts` suffix (see `core/modules/setting/graphql/types/Plugin/`) for schema
that should only be stitched into the admin GraphQL endpoint (`/admin/graphql`), never the
storefront one.

## Migrations

`src/migration/Version-<x.y.z>.ts`, default export `async (connection) => {...}`, using
`execute(connection, sql)` from `@evershop/postgres-query-builder`:

```ts
export default async (connection: any) => {
  await execute(
    connection,
    `ALTER TABLE "participant" ADD COLUMN IF NOT EXISTS "my_field" varchar DEFAULT NULL`
  );
};
```

Migrations are per-plugin, version-tracked, and run forward-only in version order the next
time the app boots — there's no down-migration mechanism, so write migrations to be safe to
re-run (`IF NOT EXISTS`, etc.) and never destructive by default.

## Reaching framework code from server-side (non-bundled) files

`bootstrap.ts`, API handlers, services and migrations run as plain compiled JS directly under
Node — they are *not* webpack-bundled, so the `@components` / `@evercamps/evercamps` aliases
don't apply there. Since `core/` and `includes/` are compiled together into one root `dist/`
folder, and your plugin's own `src/` compiles into its own `dist/` several levels below the
repo root, you reach shared framework code with a relative import into the root `dist/`:

```ts
// content/plugins/my-plugin/src/bootstrap.ts
import { addProcessor } from '../../../../dist/lib/util/registry.js';
```

Both existing plugins centralize every one of these into a single `src/core.ts` (see
`woocommerce-import/src/core.ts`) that re-exports everything the plugin needs, so the rest of
the plugin does a plain relative import (`../../core.js`) instead of re-deriving the
four-levels-up path in every file. Do the same in new plugins.

## Writing a new plugin — checklist

1. `mkdir content/plugins/my-plugin/src` and add `package.json` + `tsconfig.json` (copy from
   `national-number-field`, rename).
2. Add a `src/bootstrap.ts` with at least an empty default export.
3. Register it in `config/default.json` → `system.extensions` (`enabled: true` while you
   develop it).
4. `npm install` from the repo root (picks up the new workspace member).
5. Build whatever you need — a hook in `bootstrap.ts`, a page override, an API route, a
   GraphQL type, a migration — following the sections above.
6. `npm run dev` from the repo root; the watcher swc-compiles your `src/` on change same as
   `core/`/`includes/`. Confirm your feature works, then `npm run build && npm run start` to
   confirm it also works from a production `dist/` build (`npm run compile` inside your plugin
   folder, or the root build, produces that `dist/`).
7. Once merged, an admin can enable/disable it from `/plugin-management` without touching
   `config/default.json` again.
